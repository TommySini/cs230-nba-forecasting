# Forecaster model audit for the Claude collection expansion

Prepared 2026-11-03 UTC from official model cards, release announcements, documentation, and read-only inspection of this worktree. No models were downloaded, no paid calls were made, and no training code or configuration changed.

**Recommendation:** retain the existing pinned Qwen2.5-14B control; prioritize **gpt-oss-20b** as the first new trainable candidate, with **Gemma 3 27B IT** as an alternate. **Qwen2.5-32B-Instruct** is an optional, lower-integration-risk scale control if the project prioritizes release-bounded temporal evidence. This is an engineering and temporal-eligibility shortlist, not evidence of superior NBA forecasting. The existing 14B joint probability/explanation fit has not run. Under the shared $150 spending ceiling, select one main trainable candidate after compatibility and token-budget checks rather than promising multiple full fits. GPT-oss-120B is a possible larger quality reference if separately affordable, not a demonstrated NBA quality ceiling.

The proposed raw split is 1,592 TRAIN games through 2023–24, 223 DEV games in 2024–25, and 182 TEST games in 2025–26. These are collection counts, not a verified pregame cohort. In particular, the parallel provenance audit flags 80 of 252 HTML records as modified after cutoff. Final eligibility, exact dates, source tiers, and booster-history availability must be resolved before a model or compute budget is frozen. See [the provenance review](provenance_review.md).

Two distinct temporal claims must remain visible. A checkpoint demonstrably published before every DEV/TEST game cannot have learned those later outcomes during its creation. A later checkpoint with an earlier *declared knowledge cutoff* is useful evidence, but a pretraining cutoff does not independently date every post-training example, synthetic teacher response, or tool trace. Pinning a later checkpoint makes execution reproducible; it does not move its creation into the past. Use separate release-bounded and declared-cutoff evidence tiers, and do not quietly change the DEV season to accommodate a preferred model.

**Qwen2.5-32B is the practical scale control.** It uses the same dense decoder family and familiar Transformers causal-LM interface as the existing worker. Its card supports long context, but the repository's default configuration and any YaRN extension must be recorded rather than treating the advertised maximum as the training configuration. The 32B model has Apache 2.0 licensing; the 72B variant instead uses the Qwen license. [32B card](https://huggingface.co/Qwen/Qwen2.5-32B-Instruct), [72B card](https://huggingface.co/Qwen/Qwen2.5-72B-Instruct)

Engineering estimate: a 32B NF4 base with LoRA and the small residual head is a plausible one-H100-80GB target, but our actual long-context peak and throughput measurements cover 14B only. Rough nominal raw-weight storage is 16 GB at four bits for 32B and 36 GB for 72B, before quantization metadata, nonquantized tensors, activations, optimizer state, and runtime workspace. These arithmetic lower bounds are not memory guarantees. The 72B control preserves temporal comparability but adds enough memory/runtime risk that it should not be the first custom fit under $150. Existing AWQ teacher weights are not the same thing as an approved PEFT training base.

**GPT-oss-20b is a credible challenger, not a drop-in replacement.** OpenAI describes about 21B total and 3.6B active parameters. Native MXFP4 inference can fit 20B in 16 GB; 120B can run inference on one 80 GB GPU. Those are inference claims. They do not demonstrate that 120B joint LoRA/head training fits one H100. [20B documentation](https://developers.openai.com/api/docs/models/gpt-oss-20b), [release hardware claims](https://openai.com/index/introducing-gpt-oss/)

OpenAI's Transformers fine-tuning example does establish a useful starting point: one H100 80GB, `Mxfp4Config(dequantize=True)`, BF16, gradient checkpointing, LoRA, and a **2,048-token** sequence limit. It explicitly targets MoE expert parameters as well as linear modules. This supports short-sequence 20B trainability; it does not validate our 16K examples, prefix Brier pass, explanation CE pass, or checkpoint replay. Its reported tutorial runtime must not be extrapolated directly to NBA data. [Official fine-tuning recipe](https://developers.openai.com/cookbook/articles/gpt-oss/fine-tune-transfomers)

The model uses Harmony roles, channels, and termination conventions, and its context limit is 131,072. Our worker's Qwen chat assumptions, EOS handling, completion-only mask, base-model hidden-state access, and expert LoRA targets all need explicit adaptation and testing. Freeze reasoning effort and the distinction between an explanation target and any reasoning channel. The probability head must still read the last pregame-prefix state, before any teacher-forced explanation or reasoning. [Architecture and Harmony](https://deploymentsafety.openai.com/gpt-oss)

Read-only local inspection found `transformers==4.51.3`, `peft==0.15.2`, hard-coded NF4 loading, default `q_proj/k_proj/v_proj/o_proj` adapters, and direct `model.config.hidden_size`/base-model hidden-state access. These are validated Qwen implementation choices, not a generic guarantee for every open model. GPT-oss requires a separately pinned compatible image and actual adapter/head/replay validation. The 120B model is an interesting quality reference, but its larger resident weights and unvalidated training path make it an unsuitable first $150 custom-training commitment.

**Gemma 3 27B is the second new candidate if a second architecture is affordable.** Its 128K context and published August 2024 cutoff are attractive; no NBA-quality superiority follows from them. Its instruction format has user/model turns rather than a native system turn, so system instructions must be deliberately folded into the first user input. The multimodal wrapper/text backbone, nested configuration, prefix-state extraction, masks, and adapter export also require compatibility work. [Model card](https://ai.google.dev/gemma/docs/core/model_card_3), [Google's formatting guide](https://ai.google.dev/gemma/docs/core/prompt-structure)

A quantized 27B one-H100 fit is an engineering possibility, not a measured result here. Gemma's access/license terms must be accepted through the official distribution. Under the present cap, first qualify the officially demonstrated short-sequence GPT-oss-20B fine-tuning path before committing to a second full fit. Qwen2.5-32B remains an optional scale control, not an extra required run. See the [official weights and access conditions](https://huggingface.co/google/gemma-3-27b-it).

Qwen3 remains useful if the evaluation dates change for a scientific reason. The 32B card specifies 32.8B parameters and 32,768 native context, extendable with YaRN. The July 30B-A3B model has 30.5B total/3.3B active parameters and native 262,144 context. MoE active count does not mean only 3.3B weights must reside in memory, and its expert adapter policy introduces another experimental choice. Neither card supplies the missing earlier cutoff for the proposed DEV season. [32B](https://huggingface.co/Qwen/Qwen3-32B), [30B-A3B-2507](https://huggingface.co/Qwen/Qwen3-30B-A3B-Instruct-2507)

**GPT-4o is an API comparison, not the same trainable-head experiment.** Its official page lists October 1, 2023 cutoff, 128K context, and $2.50/M input plus $10/M output standard pricing. A named August 6, 2024 snapshot also predates the proposed DEV season. The API does not expose the backbone's trainable hidden states for our custom probability head; prompted probabilities or API fine-tuning are different baselines and must be described accordingly. Account access is unverified. [Model documentation](https://developers.openai.com/api/docs/models/gpt-4o)

Current official deprecations schedule the August/November 2024 GPT-4o snapshots for shutdown January 14, 2027; the May 2024 snapshot was scheduled to shut down October 23, 2026. Check availability before planning a run, preserve exact snapshot identity, and never silently substitute a newer model while retaining the old cutoff claim. [Deprecation schedule](https://developers.openai.com/api/docs/deprecations)

Before execution, resolve each selected historical repository revision to a full immutable SHA and hash the weights, tokenizer, chat template, and generation configuration. The existing 14B experiment already pins `cf98f3b3bbb457ad9e2bb7baf9a0125b6b88caa8`; this audit does **not** install or freeze new candidate pins. The 32B/72B September 2024 histories establish historical candidates, not authorization to use mutable `main` today. Keep tokenizer-only changes visible too.

Preserve the BAM comparison when choosing a model: exact same eligible games and booster probabilities; zero-initialized correction head; frozen-reader control; completion-only explanation loss; chronological research adapters; no held-out gold report in forecast inputs; DEV-only selection including zero correction; predictions locked before TEST labels; paired date-bootstrap differences. Inference-time researchers, reviewers, and repair models need the same temporal eligibility policy as the forecaster. A train-only hindsight teacher has a different role and must remain isolated. Pregame source timestamps cannot erase future facts already present in model weights.

The $150 ceiling remains shared with prior/active reservations, rather than $150 newly available for each candidate. No full-run cost is established for these replacements. Count all folds, final researcher training, generation and repairs, gold/review costs, forecast training/control/evaluation, startup, and any new download/storage charges. The previous 14B speed measurements are not measured GPT-oss/Gemma/32B rates; larger raw collection counts do not imply the whole expanded pipeline fits. First finalize the strict cohort and token-length distribution, then price one chosen implementation against the durable ledger.

Confidence is high in the cited release/cutoff statements and current worker-specific integration gaps; moderate in one-H100 feasibility estimates for 27–32B quantized LoRA; and presently unknown for relative NBA Brier, calibration, long-context peak memory, and full-run cost. A well-controlled 14B result is more informative than an uncompleted larger-model plan, while a validated 32B or GPT-oss-20B run would answer a useful next comparison.
